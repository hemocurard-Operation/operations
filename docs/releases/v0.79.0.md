# v0.79.0 — Uso simplificado y compras por sucursal

## Formularios y automatización

Requisiciones muestra primero insumo aprobado y cantidad. Se elimina el código manual: el servidor genera un código único y conserva responsable, fecha y prioridad por defecto. La interfaz sugiere área según el rol y deja fecha, prioridad, área y justificación en detalles plegables. Una única sucursal asignada se fija sin selector. Los reintentos conservan una clave y no duplican solicitudes; se mantienen aprobación, catálogo revisado y guardado atómico.

Compras y cotizaciones fijan la sucursal del perfil para responsables de sucursal. Al elegir un artículo del catálogo en compras o cotizaciones se completan descripción, unidad y referencia. Las fechas y condiciones de la orden se agrupan en detalles plegables. El proveedor exige inicialmente razón social; los datos adicionales quedan plegados. Los precios, vigencia, condiciones del proveedor y aprobación siguen requiriendo información real y revisión humana; no se inventan datos del PDF ni importes.

## Aislamiento del servidor

Proveedores y evaluaciones incorporan branch_id. Solo el súper usuario tiene acceso financiero entre sucursales; otros perfiles operan la sucursal asignada, aunque otro rol les conceda alcance amplio. Políticas restrictivas protegen pedidos, cotizaciones, PDF, decisiones, recepciones y requisiciones. Los detalles dependen del encabezado protegido. Se refuerzan también las funciones SECURITY DEFINER y los triggers, evitando que la API eluda el alcance. El desempeño de proveedores usa security_invoker. La lectura de evaluaciones y novedades exige también permiso del módulo; pertenecer a una sucursal no concede acceso por sí solo.

Los proveedores nuevos pertenecen a la sucursal seleccionada. Para registros antiguos, la migración asigna una sucursal únicamente si documentos existentes identifican una sola de forma inequívoca. Los registros ambiguos permanecen sin reasignar y no se exponen a responsables locales. La precomprobación del proyecto conectado encontró cero proveedores y evaluaciones; no se crean proveedores ni pedidos reales durante la validación.

## Entrenamiento igual a la aplicación

Se retira la maqueta paralela de menús y tarjetas. La vista del usuario carga mountLayout, el mismo router, agrupación de módulos, Mi trabajo y formularios que la aplicación normal, con permisos y sucursal del perfil elegido. Los cambios futuros de interfaz se reflejan en ambos contextos.

El entrenamiento conserva un marco de origen aislado con CSP sin red, adaptador que rechaza escrituras y formularios sin guardar. Usa registros vacíos y referencias de práctica claramente identificadas, no la sesión ni registros reales del usuario. La sesión del administrador permanece activa y separada; no se simula autenticación ni se concede autoridad del súper usuario a otra cuenta. La administración sensible continúa en la sesión original.

## Verificación

818 comprobaciones PostgreSQL en base aislada, incluidas lectura de contactos, evaluaciones, pedidos y PDF de otra sucursal, intentos de API con roles amplios, creación de proveedores propios, código automático, reintento y acceso global del súper usuario. Pruebas de navegador de compras, cotizaciones, requisiciones, entrenamiento real, aislamiento de sesión/red/escritura, revocación, escape de nombres y móvil; sintaxis, contratos, presupuesto UX y linter de migración. Políticas aplicadas y verificadas en producción sin nuevos avisos de seguridad. Las aprobaciones clínicas y legales pendientes no se firman ni cambian de estado.
